۱. خلاصه مدیریتی

شهیدپورتال نباید صرفاً یک خبرگزاری، سایت یادبود یا سامانه خدمات باشد. هدف، ایجاد یک لایه اتصال و راهبری برای اکوسیستم پراکنده حوزه شهدا و ایثارگران است؛ لایه‌ای که خدمات، سازمان‌ها، مراکز، داده‌ها، روایت‌ها، میراث، پژوهش‌ها، خانواده‌ها، خیرین، داوطلبان و پروژه‌های مردمی را قابل کشف، قابل اتصال و قابل هماهنگی کند.

از «مجموعه‌ای از سامانه‌ها و فعالیت‌های پراکنده» به «یک اکوسیستم قابل کشف، قابل اتصال، قابل هدایت و قابل هماهنگی» برسیم.

۲. مسئله اصلی

پراکندگی خدمات

کاربر ممکن است برای یک نیاز با چند سازمان و سامانه مواجه شود و نداند مسیر صحیح کدام است.

پراکندگی اطلاعات شهدا

اطلاعات میان پرونده‌های رسمی، رسانه‌ها، آرشیوها، خانواده‌ها و پروژه‌های مردمی قرار دارد.

پراکندگی روایت و میراث

وصیت‌نامه، خاطره، عکس، فیلم، صوت، نامه و کتاب اغلب به یک مدل داده مشترک متصل نیستند.

پراکندگی جغرافیایی و سازمانی

استان‌ها، مراکز، موزه‌ها، تشکل‌ها و مؤسسات ظرفیت‌های متفاوت و جزیره‌ای دارند.

اعتبار داده

باید داده رسمی، خانوادگی، متخصص، مردمی و تأییدنشده از هم قابل تشخیص باشد.

موازی‌کاری

تکرار پروژه‌ها و داده‌ها بدون استاندارد مشترک باعث اتلاف ظرفیت و دشواری نگهداری می‌شود.

۱۶. نقشه راه

  1. فاز صفر: معماری، حکمرانی، Taxonomy، Ontology، مدل داده و اعتبارسنجی.
  2. فاز یک: خانه، جست‌وجو، دانشنامه، خدمات، مراکز، نقشه، روایت، گنجینه، فرهنگ و رسانه.
  3. فاز دو: حساب خانواده و مشارکت.
  4. فاز سه: اتصال سازمان‌ها، ارائه‌دهندگان، API و ارجاع.
  5. فاز چهار: مرکز هماهنگی، پایش و تحلیل شکاف.
  6. فاز پنج: داوطلب، خیر، خادم، تشکل و پروژه‌های مردمی.
  7. فاز شش: Knowledge Graph، Semantic Search و AI.
  8. فاز هفت: اکوسیستم کامل، اپلیکیشن، داشبوردهای تخصصی و اطلس ملی.

۱۹. تعریف نهایی پروژه

شهیدپورتال یک زیرساخت دیجیتال یکپارچه برای کشف و دسترسی به خدمات، اتصال ارائه‌دهندگان، هدایت و هماهنگی فعالیت‌ها، توانمندسازی خانواده‌ها و ایثارگران، حفظ و توسعه میراث و روایت‌های شهدا، توسعه مشارکت اجتماعی و ایجاد شبکه‌ای قابل اعتماد از داده، دانش، مراکز و ظرفیت‌های حوزه ایثار و شهادت است.

اصل بنیادین: شهیدپورتال یک سایت دیگر نیست؛ یک لایه اتصال و راهبری برای یک اکوسیستم پراکنده است.

۲۰. معماری تجربه و مسیرهای کاربر

شهیدپورتال باید از «منوی سازمانی» به «مسیر مبتنی بر نیاز» حرکت کند. کاربر ابتدا مسئله خود را بیان می‌کند و سامانه، مسیر مناسب را می‌سازد.

مسیر خدمت

نیاز ← تشخیص موضوع ← خدمت ← شرایط ← مدارک ← ارائه‌دهنده ← ارجاع ← پیگیری ← نتیجه ← رضایت‌سنجی.

مسیر پژوهش

جست‌وجو ← پرونده شهید ← شبکه منابع ← تشخیص سطح اعتبار ← درخواست دسترسی ← دریافت منبع.

مسیر مشارکت

نیاز فعال ← انتخاب پروژه ← نوع مشارکت ← ثبت تعهد ← انجام ← گزارش اثر.

مسیر روایت

ثبت روایت ← اطلاعات راوی و منبع ← بررسی ← اتصال به پرونده ← انتشار یا آرشیو.

اصل UX: نام سازمان نباید پیش‌نیاز یافتن خدمت باشد؛ کاربر باید بتواند با زبان طبیعی بگوید «چه می‌خواهم؟» و یک مسیر قابل فهم دریافت کند.

۲۱. مدل حکمرانی و نقش متولیان

  • مالک/مرجع داده: نهادی که بر اساس قانون و مأموریت، اختیار داده را دارد.

شاخص‌های فعال‌سازی: تکمیل اولین مسیر، دریافت اولین خدمت، اولین مشارکت، اولین اصلاح داده و بازگشت کاربر؛ نه صرفاً تعداد ثبت‌نام.

۲۴. معماری فنی و زیرساخت

Web / PWA / Apps
API Gateway
Domain Services
Data & Search
Integration

معماری پیشنهادی، API-First و ماژولار است:

  • تجربه: وب RTL، PWA و در آینده اپلیکیشن‌های تخصصی.
  • سرویس‌ها: جست‌وجو، هویت، خدمات، ارجاع، محتوا، نقشه، پیام، پرونده و هوش مصنوعی.
  • داده: PostgreSQL، موتور جست‌وجو، Object Storage، PostGIS و در مرحله بلوغ Knowledge Graph.
  • یکپارچه‌سازی: REST/GraphQL، Webhook، ETL/ELT و صف پیام متناسب با نیاز سازمان‌ها.
  • امنیت: IAM، MFA برای نقش‌های حساس، رمزنگاری، Secret Management، Audit Log، پشتیبان‌گیری و Disaster Recovery.
اصل معماری: ابتدا مدل دامنه و قرارداد API تثبیت شود؛ انتخاب فناوری دقیق پس از ارزیابی بار، هزینه، مهارت تیم و الزامات حاکمیتی انجام شود. بنابراین Next.js، FastAPI، Neo4j، Elasticsearch یا Kubernetes «گزینه» هستند، نه الزام معماری.
