# معماری کلان شهیدپورتال

## ۱. تعریف محصول

شهیدپورتال یک بستر مستقل و یکپارچه برای گردآوری، نگهداری، مدیریت و ارائه اطلاعات، خدمات، آثار و فعالیت‌های مرتبط با شهدا و خانواده‌های معظم شهدا است. ساختار آن به‌صورت «هسته مرکزی + مراکز تخصصی» طراحی می‌شود؛ هر مرکز دامنه کاری و داده‌های مستقل دارد، اما از هویت، دسترسی، رسانه، جست‌وجو، گردش‌کار و گزارش‌گیری مشترک استفاده می‌کند.

بانک شهدا یکی از مراکز محوری شهیدپورتال است و نباید به‌عنوان یک وب‌سایت جداگانه و بی‌ارتباط توسعه داده شود.

## ۲. اصول معماری

- استقلال اجرایی شهیدپورتال از سامانه‌های دیگر در فاز نخست.
- طراحی ماژولار و قابل توسعه؛ هر مرکز بتواند در آینده به‌صورت سرویس مستقل نیز ارائه شود.
- جداسازی پنل مدیریت از وب‌سایت عمومی و API.
- نگهداری داده‌ها با شناسه‌های پایدار و روابط روشن؛ عدم اتکا به عنوان یا نام به‌عنوان شناسه.
- ثبت تاریخچه تغییرات، ایجادکننده، ویرایش‌کننده، زمان و وضعیت انتشار.
- پشتیبانی از پیش‌نویس، بررسی، تأیید و انتشار.
- کنترل دسترسی مبتنی بر نقش و محدوده سازمانی/مرکز.
- حفظ فایل‌ها و مسیرهای رسانه‌ای فعلی تا زمان مهاجرت کنترل‌شده.
- فارسی و RTL به‌عنوان زبان و جهت پیش‌فرض رابط کاربری.
- استفاده از فونت‌های محلی مخزن؛ عدم وابستگی به CDN و فونت خارجی.
- رابط روشن، رسمی، خلوت و واکنش‌گرا؛ پشتیبانی از نمایش موبایل.
- جداسازی تاریخ نمایشی شمسی و ارقام فارسی از مقادیر استاندارد ذخیره‌سازی و API.

## ۳. هسته مرکزی

### مدیریت مجموعه
- نمای مدیریتی کلان و شاخص‌های هر مرکز
- تعریف مراکز، زیرمجموعه‌ها و واحدهای سازمانی
- فعال/غیرفعال‌کردن مرکزها و تنظیمات اختصاصی هر مرکز
- مدیریت کاربران، نقش‌ها، مجوزها و دامنه دسترسی
- گزارش فعالیت کاربران و رویدادهای امنیتی

### خدمات مشترک
- مدیریت رسانه و فایل‌ها با متادیتا و سطح دسترسی
- جست‌وجوی یکپارچه در داده‌های مجاز
- اعلان‌ها و پیام‌های سیستمی
- گردش‌کار ثبت، بررسی، تأیید و انتشار
- ثبت تاریخچه و سوابق تغییرات
- مدیریت برچسب‌ها، دسته‌بندی‌ها و واژگان مرجع
- API نسخه‌بندی‌شده برای اتصال وب‌سایت عمومی و سامانه‌های آینده

## ۴. مراکز تخصصی

| مرکز | دامنه اطلاعات و قابلیت‌ها |
|---|---|
| بانک شهدا | پرونده شهید، مشخصات هویتی و زندگی‌نامه، تصاویر، اسناد، وصیت‌نامه، خاطرات، سوابق و ارتباطات خانوادگی با رعایت سطح دسترسی |
| سازمان‌ها و تشکل‌ها | نهادها، بنیادها، انجمن‌ها، یگان‌ها، تشکل‌ها و اعضا |
| عملیات و رویدادها | عملیات‌ها، رخدادهای تاریخی، مناسبت‌ها، یادواره‌ها و برنامه‌ها |
| گلزار و آرامستان | گلزارها، قطعات، مزارها، نشانی و مختصات جغرافیایی |
| نشر و کتابخانه | کتاب‌ها، نشریات، مقالات، اسناد و منابع پژوهشی |
| رسانه و گنجینه | عکس، فیلم، صوت، آثار، یادگارها و مجموعه‌های موضوعی |
| روایت و خاطرات | خاطرات شفاهی و مکتوب، راویان، مصاحبه‌ها و منابع مرتبط |
| خانواده و خدمات | خدمات، درخواست‌ها، پیگیری‌ها و اطلاعات مجاز مرتبط با خانواده‌ها |
| آموزش و فرهنگ | دوره‌ها، برنامه‌های آموزشی، فرهنگی و هنری |
| اشتغال و توانمندسازی | فرصت‌ها، مهارت‌ها، طرح‌ها و برنامه‌های حمایتی |
| ارتباطات و مشارکت | ارتباط مردمی، مشارکت‌ها، همکاری‌ها و پیوندهای بیرونی |

فعال‌سازی هر مرکز می‌تواند مرحله‌ای باشد. وجود یک مرکز در معماری به معنی آماده‌بودن یا انتشار عمومی آن نیست.

## ۵. مدل داده محوری بانک شهدا

موجودیت اصلی «شهید» است و سایر اطلاعات به‌صورت رابطه‌ای و قابل توسعه به آن متصل می‌شوند:

- Martyr: شناسه پایدار، نام و نام خانوادگی، نام پدر، تاریخ‌ها، محل تولد، محل شهادت، وضعیت انتشار و خلاصه زندگی‌نامه
- MartyrProfile: شرح زندگی، تحصیلات، فعالیت‌ها و اطلاعات تکمیلی
- MartyrMedia: تصاویر، صوت، فیلم و اسناد مرتبط
- MartyrDocument: وصیت‌نامه، اسناد هویتی و منابع مستند
- MartyrMemory: خاطرات، روایت‌ها و مصاحبه‌ها
- MartyrRelation: روابط خانوادگی یا سازمانی با نوع رابطه مشخص و سطح دسترسی
- Organization: سازمان، یگان، نهاد یا تشکل مرتبط
- Operation: عملیات یا رویداد تاریخی مرتبط
- Cemetery / Grave: گلزار، قطعه و محل مزار
- Source / Citation: منبع هر داده و میزان اعتبار/وضعیت بررسی آن

اطلاعات حساس خانوادگی و اسناد محدود، پیش‌فرض عمومی ندارند و فقط با مجوز مشخص قابل مشاهده خواهند بود.

## ۶. نقش‌ها و سطوح دسترسی اولیه

- مدیر کل سامانه: دسترسی مدیریتی به کل مجموعه
- مدیر مرکز: مدیریت تنظیمات و داده‌های مرکز خود
- کارشناس ثبت: ایجاد و تکمیل رکوردها
- کارشناس بررسی: کنترل صحت و مستندات
- تأییدکننده/ناشر: تأیید نهایی و انتشار
- پژوهشگر: مشاهده داده‌های مجاز و ثبت منابع
- کاربر عمومی: مشاهده اطلاعات منتشرشده

مجوزها باید در سطح عملیات (مشاهده، ایجاد، ویرایش، حذف، بررسی، تأیید، انتشار، خروجی) و در صورت نیاز در سطح رکورد/مرکز اعمال شوند.

## ۷. چرخه انتشار محتوا

1. ثبت اولیه و تخصیص شناسه پایدار
2. تکمیل اطلاعات و افزودن منبع/مستند
3. بررسی داده‌ها و رفع مغایرت
4. تأیید مسئول مجاز
5. انتشار در وب‌سایت عمومی یا API
6. ثبت تاریخچه اصلاحات و امکان بازگشت/اصلاح کنترل‌شده

## ۸. معماری فنی پیشنهادی

- CMS و پنل مدیریت: Payload CMS
- میزبانی و اجرای لایه برنامه: Cloudflare Workers، پس از آزمون سازگاری و بررسی هزینه
- پایگاه داده: Cloudflare D1 برای داده‌های ساخت‌یافته در فاز آزمایشی
- ذخیره‌سازی فایل: Cloudflare R2 برای رسانه‌ها و اسناد، پس از تعیین سیاست دسترسی و پشتیبان‌گیری
- وب‌سایت عمومی: رابط مستقل و سبک متصل به API نسخه‌بندی‌شده
- احراز هویت: در فاز نخست مستقل؛ طراحی اتصال آینده به هسته هویت مرکزی بدون وابستگی اجباری
- توسعه و انتشار: محیط محلی، آزمایشی و عملیاتی مجزا

انتخاب نهایی نسخه‌ها، آداپتورها و منابع Cloudflare باید با قالب رسمی و نسخه‌های سازگار در زمان پیاده‌سازی تطبیق داده شود. ایجاد منابع واقعی یا هزینه‌زا در Cloudflare بخشی از این سند نیست و نیازمند تأیید جداگانه است.

## ۹. برنامه اجرا

### مرحله صفر — شناخت و تثبیت
- بازبینی کامل صفحات، فایل‌ها، رسانه‌ها و لینک‌های مخزن فعلی
- تهیه فهرست مراکز و تعیین دامنه هر مرکز
- تعیین داده‌های فعلی قابل نگهداری و موارد نیازمند اصلاح
- تثبیت طراحی پایه و ساختار مسیرها

### مرحله یک — هسته اجرایی
- راه‌اندازی Payload در ساختار مستقل و قابل نگهداری
- فارسی‌سازی کامل پنل، RTL و فونت محلی
- پیاده‌سازی کاربران، نقش‌ها، مراکز، رسانه و گردش‌کار
- ایجاد API و محیط آزمایشی بدون جایگزینی سایت فعلی

### مرحله دو — بانک شهدا
- پیاده‌سازی مدل‌های اطلاعاتی و روابط
- فرم‌های ثبت، ویرایش، بررسی و انتشار
- جست‌وجو، فیلترها، پرونده کامل شهید و مدیریت رسانه
- ورود داده آزمایشی و آزمون صحت روابط و دسترسی‌ها

### مرحله سه — اتصال وب‌سایت عمومی
- اتصال تدریجی صفحات عمومی به API
- حفظ fallback برای داده‌های فعلی تا تأیید صحت API
- عدم حذف یا جابه‌جایی رسانه‌ها بدون تطبیق و تأیید

### مرحله چهار — توسعه مراکز
- افزودن مرکزها بر اساس اولویت و نیاز عملیاتی
- گزارش‌های تلفیقی و جست‌وجوی بین‌مرکزی
- آماده‌سازی API برای اتصال سامانه‌های بیرونی

## ۱۰. معیارهای پذیرش

- پنل و صفحات اصلی فارسی و RTL واقعی باشند.
- هیچ فونت یا کتابخانه ضروری از CDN خارجی بارگیری نشود.
- نقش‌ها و دسترسی‌ها در API نیز اعمال شوند، نه فقط در رابط کاربری.
- رکوردها شناسه پایدار و تاریخچه تغییرات داشته باشند.
- محتوای پیش‌نویس در خروجی عمومی نمایش داده نشود.
- رسانه‌ها، مسیرهای فعلی و محتوای موجود در مهاجرت حفظ شوند.
- جست‌وجو و فیلتر بانک شهدا بر اساس فیلدهای تعریف‌شده کار کنند.
- در موبایل و دسکتاپ چیدمان بدون سرریز افقی باشد.
- خطاهای فرم، اعتبارسنجی و وضعیت ذخیره‌سازی برای کاربر روشن باشند.
- قبل از استقرار عملیاتی، آزمون پشتیبان‌گیری، بازیابی و کنترل دسترسی انجام شود.

## ۱۱. محدوده فاز نخست

فاز نخست فقط شامل هسته مدیریت شهیدپورتال و بانک شهدا است. سایر مراکز در ساختار و منوی قابل توسعه تعریف می‌شوند، اما تا زمان آماده‌شدن مدل داده و فرایند اجرایی، نباید به‌عنوان قابلیت عملیاتی یا تکمیل‌شده نمایش داده شوند.

اتصال به مخازن و سامانه‌های دیگر از جمله adminlogin در فاز نخست انجام نمی‌شود. این اتصال باید بعداً از طریق API و قراردادهای مشخص صورت گیرد.
